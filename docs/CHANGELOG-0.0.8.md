# 0.0.8：登录态不再丢（自建凭据仓库，重载/更新/重装都保留）

> 上一版承认「登录态只在内存」，说重载就丢是必然的。这是**没实现**，不是限制：
> `dsh-connect-workbuddy` 早就用自建 vault 解决了同一件事。
>
> 这一版照它的做法做：在 `$DSH_HOME` 下建插件自己的凭据仓库。

## 根因回顾

```ts
// 旧代码 src/index.ts:111 —— 登录成功只改了内存变量
config.cookie = credential.cookie;
```

注释写着「重启后仍然有效」，但下一行没有任何写盘代码。`Config` 里的 `cookie`
只从 `cordis.patch.yml` 读初始值，而那里没有这个插件的条目 —— 所以每次重载
`resolveCookie()` 都从零开始，只能再去赌浏览器 cookie 库没被锁。

## 三个判断，以及为什么

### 1. 不用 `ctx.credentials`，自建仓库

DSH 的 `ctx.credentials` 只认两种记录：`api-key` 和 `grant`。灵犀的登录态是一串
`wps_sid=...; uid=...` 的 cookie，它既不是 API key 也不是授权 grant —— 塞进任何
一类都是在骗那个 seam。而且落盘位置由宿主实现决定，宿主换版本/换 profile 时
本插件无法保证它在哪。

自建目录的性质是明确的：**位置在 `$DSH_HOME` 根下，不属于任何插件包目录**。
`npm uninstall` / 升级重装只动 `node_modules` 和 `package.json`，碰不到它。

### 2. 仓库排在自动探测**之前**

顺序是这一版真正起作用的地方：

```
手填  →  插件仓库  →  自动探测
         ↑ 上一次成功拿到的，跨重载还在
```

排在后面就等于每次重载都重新碰运气 —— 浏览器一开着锁库，登录态就没了。
这正是你截图里「未登录 / 登录来源：无」的成因：`probe-credential.mjs` 在本机
实测就是「库被运行中的浏览器独占锁定」。

### 3. 登出只清插件那份

「忘记登录态」不该把你浏览器或灵犀客户端里的登录也退掉 —— 那是用户的登录，
不是插件的配置。插件能做的、该做的，只是「下次不再用它」。

## 升级后要做一次

仓库现在是空的（之前的登录态从没保存过），所以**第一次仍要登录一次**：

1. 重启 DSH（或重载插件）
2. 卡片「账号」页点「登录灵犀」，在弹出来的浏览器窗口里登录
3. 登录成功后仓库文件会出现在 `~/.dsh/lingxi-vault/credential.json`

之后再重载、再更新插件，都不需要重新登录。
