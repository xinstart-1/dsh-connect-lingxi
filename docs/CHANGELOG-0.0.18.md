# 0.0.18：不再自动裁剪或压缩上下文

这一版只做一件事：**把「悄悄丢历史」这个行为整个拆掉**。没有明确要求时，插件
不再裁剪、不再压缩、不再掐长消息，完整 `messages` 原样发给上游。

## 症状

长对话里会突然冒出这样一条 system 消息：

```
[历史已压缩：更早的 1260 条消息被省略（上游单次请求长度上限 320KB）]
```

从那之后模型开始「失忆」：前面确认过的文件名、报错、用户的约束都不见了；如果
开头有一次大段粘贴，还会被掐头去尾，中间内容直接消失。用户看不到任何提示，
只能感觉「它怎么突然不记得了」。

## 根因

`src/protocol/budget.ts` 按 `MAX_PROMPT_KB = 320` 的预算**主动**裁剪：

1. 单条超过 48KB 的 message 掐头去尾；
2. 整体超过 320KB 就从最老的一端整条丢；
3. 丢到开头是 `tool` 结果时继续丢，避免孤儿 tool 结果。

320KB 这个数字从来没人验证过。2026-11-11 用探针实测（`deepseek-v4.1-flash`，
单条 user 消息灌填充文本）：

| 内容 | 体积 | prompt_tokens | 结果 |
| --- | --- | --- | --- |
| 英文 | 320KB / 640KB / 1.28MB / 2.56MB / 3.84MB / 4096KB | 最多 932,102 | 全部 HTTP 200 正常 |
| 英文 | 4607KB | ≈1,048,276 | HTTP 200 正常 |
| 英文 | 4608KB（4,718,592 字节） | ≈1,048,504 | HTTP 200 + 流内 `AIError / AI服务异常` |
| 中文 | 3072KB / 4096KB（1,398,101 字） | 735,881 | 正常 |
| 中文 | 5120KB（1,747,627 字，字节数比上面失败的英文还多） | ≈920,000 | 正常 |

结论：**真实上限是 1M token 上下文**（约 470 万英文字符 / 190 万中文字符），
不是字节数——同样 4.6MB，英文失败、中文通过，因为中文字节多而 token 少。旧版
按 320KB 字节预算裁剪，实际只用到 1M 上限的约 7%。

另一个坑：超限时上游**不报 4xx**，而是 HTTP 200 里流内回 `AIError / AI服务异常`
（usage 全 0），字面上看不出是「太长」。

## 这一版做了什么

- **删掉自动裁剪**：`budget.ts` 与其单测一并移除，`buildAgentBody` 不再调用任何
  裁剪逻辑，`messages` 原样透传（只保留上游不接受的形状归一：分段 content 展平、
  `tool_choice` 降级）。
- **超限只诊断、不动手**：按实测比例估计本轮 token（`estimatePromptTokens`，
  英文 ≈4.5 字符/token、中文 ≈1.9 字符/token），达到 1M 上限的 90% 时：
  - 流内 `AI服务异常` 的错误帧末尾补一句「本轮约 X 万 token，接近 100 万上限，
    插件不会自动裁剪或压缩，请新开会话或清理历史」（`shim/server.ts` 的 `fail`）；
  - 被上游 4xx 拒绝时，`client.ts` 的 `send` 也会带同一句。
  没接近上限时，任何提示都不会出现。
- **常量换掉**：`MAX_PROMPT_KB = 320` → `MAX_PROMPT_TOKENS = 1,048,576`，注释写明
  这组实测数据。
- **契约测试**：新增 `test/no-trim.test.ts`（500KB 粘贴原样发出、40 条历史一条不丢、
  估计比例与实测对齐）；`test/shim.test.ts` 补一条「长 prompt 的 AI服务异常 会补
  1M token 说明、短 prompt 不补」。
- **文档同步**：`docs/PROTOCOL.md` §9 换成实测表格与阈值说明。

## 边界

历史真超过 1M token 时，这一轮会**直接失败**（`AI服务异常` + 一句解释），而不是
由插件替用户决定丢哪一段。需要压缩时由用户明确要求——插件不擅自做。

## 顺带：模型右侧徽标换成灵犀网页的配色

输入框模型选择器里，`NEW` / `正式版` / `首发接入` 这三个目录徽标原来由宿主按
`badge.tone` 画成蓝 / 绿 / 灰。现在按灵犀网页的样式统一成**浅橙底 + 橙字胶囊**：

| 项 | 值 |
| --- | --- |
| 底色 | `#fef1ea`（截图里徽标填充色） |
| 文字 | `#e2651a`（截图里徽标文字色） |
| 形状 | 全圆角胶囊（`border-radius:999px`），`10px/18px`，左右 `7px` |
| 范围 | 只作用于 `[data-provider-id="wps-lingxi"]` 的行 |

实现方式仍是**只注入 CSS**，不重占 `conversation.input.model.label` 槽位：

```
[data-provider-id="wps-lingxi"] [class*="badge"]:not([class*="badgedName"]){…}
```

- 宿主仍按原样画 `Tag` 与勾选状态，只有皮肤被覆盖；`tone` 保留，语义不变。
- `:not([class*="badgedName"])` 排除宿主「名字 + 徽标」的包裹层（类名里也含
  `badge`），否则整行名字都会被染上底色。
- 宿主改类名后缀时这条规则静默失效，徽标退回宿主默认配色，不会报错。

对应测试在 `test/bundle-runtime.test.ts`：断言注入的 `model-badge.css` 含
`#fef1ea` / `#e2651a` / `999px`，并且带 provider 作用域与 `badgedName` 排除。
